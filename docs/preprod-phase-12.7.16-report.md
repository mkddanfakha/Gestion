## RESTORE CHAIN

```text
Vue Index.vue → runRestore()
  → SweetAlert loading
  → Inertia router.post(admin.backups.restore)
    → Middleware auth / verified / EnsureUserIsAdmin
      → BackupController::restore()
        → checkPermission(backups.restore)          [403 possible #1]
        → validate(confirm, phrase, target, mode, acknowledge)
        → BackupPathGuard::resolveExistingBackupPath()
        → [option] safety_backup → backup:production (subprocess gestion_backup)
        → DatabaseRestoreService::restore()
          → DatabaseSafetyGuard::assertRestoreConfirmationPhrase()
          → DatabaseSafetyGuard::assertExplicitRestoreTarget()
          → DatabaseAccountGuard::assertAccountForOperation('restore')  [403 démontré]
          → BackupConcurrencyGuard::runRestore()
            → BackupArchiveInspector::inspect()
            → extract SQL → storage/app/restore-temp/
            → MysqlPdoDumpImporter::import() (PDO, DROP/CREATE allow-list DB)
        → catch ProtectedDatabaseException → abort(403)
        → catch RuntimeException → redirect flash.error ou abort(409)
        → success → redirect flash.success (302)
```

**Constat architectural :** le backup utilise `PrivilegedProcessRunner` (subprocess + `gestion_backup`), mais **aucun subprocess restore** n’existe. La restauration HTTP s’exécute dans le processus Laravel connecté en `gestion_app`.

## ROOT CAUSE

```text
DEMONSTRATED
```

### Explication

Le flux HTTP de restauration s’exécute dans le processus Laravel connecté en **`gestion_app`**.  
`DatabaseRestoreService::restore()` appelle immédiatement :

```php
DatabaseAccountGuard::assertAccountForOperation(OPERATION_RESTORE);
```

qui exige **`gestion_restore`**. L’écart provoque `ProtectedDatabaseException`, transformée en **`abort(403)`** par `BackupController::restore`.

Contrairement au backup (qui passe par `PrivilegedProcessRunner` + subprocess `gestion_backup`), **aucun runner privilégié restore** n’est branché sur la route UI.

---

## SECONDARY CAUSES

1. **Safety backup échoué** (audit id=102, `safety_backup_failed`) — bloque avant restore si l’option est cochée.
2. **Permission `backups.restore` manquante** — `abort(403)` en amont (non observé sur user_id=1).
3. **Cible `gestion` ou hors allow-list** — `ProtectedDatabaseException` (non observé ; cible auditée = `gestion_test`).
4. **Absence de fichier credentials restore** — pas de `.mysql-gestion-restore.local` ni loader dédié (architecture incomplète pour HTTP restore).
